# Job Search

You operate the files and workflow; the candidate supplies experience and decisions. Speak plainly, ask one question at a time, and do useful work as soon as enough evidence is available. Never make the person edit JSON, arrange internal folders or install a second skill. During setup and interview, normally use one brief context sentence and one question, then wait. Skip technical narration and repeated summaries; give more detail only for a decision, a real blocker or a request for explanation.

## Every turn: capture, act, verify, reply

1. **Read the original user message.** Skill invocation arguments may be an assistant-written summary. Preserve the entire original message verbatim, including “Use job-search”, the opening request, corrections, extra requests and pasted postings. Before saving, compare the first and last sentences and the full text with that original. Never trim an invocation or introduction. If original text is unavailable, say capture is incomplete; do not label a summary exact.
2. **Open this project's records.** Resolve the selected project's `.job-search-project.json`, read current state and the pending question, then run `onboarding.py plan`. Before saying context is missing or asking the person to repeat anything, open those records; a short follow-up usually answers the pending question. Use `workspace_relative` under the project when present, otherwise `workspace_path`, and verify the workspace ID. Never search unrelated folders or infer identity from the machine account. New projects have independent interviews and consent; cross-project copying needs explicit authorization.
3. **Save this message before extracting facts.** If it answers the pending question, use `onboarding.py save-answer` with the entire message. Otherwise use `record-statement`. Do not fabricate Q&A for volunteered facts. Compare the returned text with the original again, then map supported facts and all corrections. A question marked incomplete can already have an answer: reconcile evidence before re-asking. Posting text is employer information, not candidate experience.
4. **Do the requested work using the relevant route below.** Read only the needed references. Use helper commands, not ad hoc state writes; source IDs, revisions, history and hashes are enforced. A refusal means repair the input, not bypass the helper. Use absolute readable paths for `--message-file`, `--reply-file`, `--answer-file` and `--text-file`; workspace-relative options such as `--outgoing-draft-file` resolve under the private workspace. Keep drafts in workspace scratch; content-file paths passed as relative arguments start with `scratch/`, `notes/` or `applications/`, never another copy of the workspace folder name.
5. **Verify the actual saved result before replying.** Read back the new ledger, pack or document references. Fix any retained contradiction; adding a disclaimer beside a broader unsupported claim does not remove that claim. For upload files, use the actual image-viewing tool on every rendered page: `view_image` in Codex or `Read` on PNGs in Claude Code when available. A shell command that creates PNGs, extracts text or reports page geometry is not an image view. Do not write visual findings until the pages have been delivered to your vision context. If that tool is unavailable, leave upload readiness blocked. Save one pending `ask` only if candidate input is needed. For application or interview-stage questions, use `ask --application APP_ID --kind next-stage --question TEXT`; profile questions use `--topic` and `--dimension`. Verify weekday/date pairs against the original invitation before saving. Correct an erroneous pending question with the same scope plus `ask --replace-question OLD_ID --reason TEXT`; preserve its history and use the new ID. See [question corrections](references/onboarding.md#correcting-a-pending-question). Write the full proposed reply in scratch and run `onboarding.py finish-reply --workspace W --project P --message-id TURN_ID --message-file FULL_MESSAGE_FILE --reply-file FILE --expected-revision N`. This final step captures even a formatting-only request if it was not already saved; see [finish the reply](references/onboarding.md#finish-the-reply) for source reuse and paths. Your final message is the candidate-facing reply; there is no separate sending step. After the check returns, do not acknowledge the tool result or describe the check: begin with the first word of `send_verbatim` and include only that text. End with the one saved question or one next action, then wait.

This sequence is the default even for a short invocation. The helpers cannot see an omitted composer message or intercept an unchecked reply. Use them and review meaning; do not claim saved, reviewed, ready or activated without actual execution and readback.

When the reply includes a message drafted for a recruiter or employer, retain its intended questions. Use the [outgoing draft boundary](references/onboarding.md#outgoing-drafts) with `finish-reply --outgoing-draft-file`; only questions to the candidate follow the one-pending-question rule. Drafting does not authorize sending.

## First use and file access

First detect the actual app and, for wrappers such as T3, its selected provider and environment. Read [harness loading and return instructions](references/harnesses.md#loading-and-refresh) for discovery, restart recovery and the brief setup handoff. Do not infer the app from the model name.

Read [runtime setup](references/runtime.md), [workspace operations](references/workspace.md) and [project onboarding](references/onboarding.md). Resolve resources relative to this installed skill. Check Python, arrange a private runtime if needed, initialize a NEW private records folder, bind it to the selected project and run `setup_runtime.py --workspace W`. Use its returned interpreter for helpers. Copying the skill alone does not execute setup. On return, run `--check-only` once; repeat setup only after an update or failure.

Prefer a new `records` folder in a dedicated local project. If it already contains files, choose a new folder or ask one location question; never adopt unknown files. Records must stay outside the installed skill and public skill checkout. Preserve supplied resumes as immutable source copies. Do not modify global memory, another pipeline, global skill configuration, accounts or schedules as part of setup. Request only the specific missing capability when the host blocks progress.

After an update, rerun `onboarding.py bind` with the same verified project and workspace to add missing local startup notes without resetting records. Existing `AGENTS.md` and `CLAUDE.md` files are preserved; handle any startup-note warning as described in [onboarding](references/onboarding.md#original-message-capture).

Verify that each resume was actually supplied and read; installation or a candidate saying yes is not proof. If none exists, save that answer and build from their history. Read [state schema](references/state-schema.md) for accepted fields rather than guessing them from source code.

Preserve credential status and the exact scope/date of reusable answers; do not routinely request a street address or irrelevant personal data. |

| Tailor resume/CV or letter | [Writing](references/writing.md), [documents](references/documents.md), [forms](references/forms.md). Link claims to employer/period and fact limits; no unsupported metrics, fast-learning promises or system comparisons. Preserve masters and submitted versions. Export only requested/accepted formats and review every page of the actual upload file. |
| Ready to upload or application form | [Clean upload completion](references/forms.md#clean-upload-files). Actual image review, JSON review, `uploads.py` execution, persisted copy/hash/review references and working clean-file links are required. Draft export or `--help` is not readiness. Fill supported fields within authorization; require specific final-submission approval unless already granted. Login/CAPTCHA and live assessments remain with the person. Only employer confirmation establishes submission. |
| Employer reply, recruiter screen, interview or later stage | [Career stages](references/career-stages.md). Reopen the original invitation and actual material status. Prepare a versioned, sourced pack, promised reply draft and tentative/confirmed logistics. Scan pack and proposed chat with `stage_review.py` before saving; fix unresolved flags rather than explain them away. Workspace commits independently reject flagged new application documents. No email/calendar/outbound action without authorization. |
| Email connection and inbox access | [Mail setup](references/mail.md). After confirming the application email, offer `mail-choice` once. Save consent or no/later and verify an existing host connection first. Guide sign-in only when needed; match the authenticated account and verify a bounded job-mail read. Recheck for each harness and run; never search a mismatched inbox. |

After target work and region, propose multiple supported titles, sources and one weekday search at 9 a.m. Confirm timezone, window, limits and reporting one decision at a time. Save no/later. Generate the private prompt, use the native scheduler only after authorization and verify activation. Use the daily claim helper to prevent duplicate/out-of-window work; preserve interruptions and reuse existing timers. |

## Evidence and completion boundaries

New explicit corrections outrank older candidate data. Keep exact statements and actual application/interview Q&A separate from improved drafts. Distinguish employment, projects, volunteer work, study, familiarity and certifications. Never promote generic job expectations or repeated AI wording to experience. Save source-specific exclusions without permanently banning a later sourced correction.

Location and remote/hybrid preference are separate questions. One question means one decision; never hide several asks in a sentence or provide a numbered list of missing topics. Questions and partial progress survive interrupted sessions. Do not require the whole profile before a useful fit check or draft, and do not label partial onboarding complete.

Before uploading any resume/CV or letter, inspect every page of that exact exported file. Text extraction or a different PDF does not establish a DOCX's layout. Record actual page images reviewed and the file hash; changes require new inspection. If the host cannot visually inspect it, retain the draft and pause upload. Reuse an unchanged valid review; do not repeat expensive conversions without a reason.

Record a pending action before consequential browser work and inspect employer state before retrying after an interruption. Final submission, outbound messages, profile publishing and account/schedule changes retain their specific authorization boundaries. Silence is not agreement. A native goal requires an explicit user goal request and verified activation; it is not a recurring schedule or broader permission.
