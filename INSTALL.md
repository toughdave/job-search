# Instructions for the installing AI

Install and start this skill for the person; do not turn this file into a manual questionnaire or a list of shell commands for them.

1. Detect the current harness, project, file permissions, installed skill and usable runtimes. Read the repository before executing its helpers. Do not inspect unrelated personal projects. Reuse an existing project skill if its release matches. Before either installation method below, preserve any differing installed copy and inspect its differences. Obtain update authorization if it is not already provided; never silently overwrite local customizations.
2. Prefer project-scoped installation. With Node >=22.20, run `npx skills@1.5.26 add toughdave/job-search --skill job-search --agent codex --copy -y` for Codex, or replace `codex` with `claude-code` or `opencode`. For T3 Code, detect its selected provider and environment and use that provider target; there is no `t3` target in this installation recipe. Do not infer a provider from the model name. Install multiple targets only when requested. Never install globally by default. The user may need to approve network access or installation under their harness policy.
3. Without a compatible Node, download a tagged release or a temporary shallow Git checkout. In the release's attached skill ZIP, the complete skill is the extracted `job-search` folder; in a source checkout or GitHub source archive, it is `skills/job-search`. Locate the folder containing SKILL.md plus references, scripts and assets, and copy that **entire** folder into `.agents/skills/job-search` (Codex) or `.claude/skills/job-search` (Claude Code), or `.opencode/skills/job-search` (OpenCode), inside the selected project. In T3, use its selected provider's project path. OpenCode also reads compatible `.agents/skills` and `.claude/skills`; reuse a valid existing copy rather than adding duplicates. Never copy the candidate's resume into that installed directory. Do not pipe uninspected remote text into a shell. Refuse to replace a differing existing install silently: preserve it, inspect differences, and confirm an update if required.
4. Open the installed SKILL.md and check that its relative references, `scripts/workspace.py`, `scripts/onboarding.py`, `scripts/documents.py`, and document assets exist. Use the harness's skill listing/selection to verify discovery when available. A copied file alone is not evidence that discovery worked. Continue in this conversation by reading the installed instructions when possible. Native discovery and direct file loading are different: verify the picker/tool separately. Read the installed `references/harnesses.md` for app-specific refresh rules; ask for a new conversation or affected app/provider restart only when needed. Before any restart, save the project/records location and pending action; never claim to have activated an unavailable shortcut.
5. Begin onboarding by checking actual attachments and supplied file paths; do not assume a resume arrived. Let the skill initialize a NEW private workspace and bind its interview to the actual selected project using `scripts/onboarding.py`. Keep it outside this repository and outside any installed skill directory. Prefer a new `records` subfolder in the dedicated project; a private sibling is also supported. Read an existing `.job-search-project.json` pointer before initializing anything. `bind` creates this pointer for the next conversation. If write permissions prevent setup, ask for one writable location. Never reuse an unrelated existing job pipeline. If no resume was supplied, ask whether one exists; help build one if not. One-question pacing and file management are built-in defaults. No global memory, personal skill, account connection, permission mode or schedule is changed by installation.

Keep candidate-facing setup updates to a short outcome or necessary action. Do not narrate dependencies, helper commands or every file operation. Ask one decision at a time and wait; use the skill's setup handoff to show only this person's return command.

## Set up the runtime after copying the skill

Copying a skill does not execute an installation hook or install its runtime. After copying, open the installed [runtime setup reference](skills/job-search/references/runtime.md) and follow it. Resolve an available Python 3.9+ interpreter; if absent or unusable, install a private maintained Python using the documented uv route. Do not make the beginner research or type package commands. Node is optional: prefer the download-and-copy route when it is absent, rather than installing Node solely to copy files.

Use that interpreter for the standard-library workspace initialization and binding. Run the installed `scripts/setup_runtime.py --workspace W`; it creates the private environment, installs the shipped requirements, verifies imports/timezones, creates and reopens DOCX/PDF samples, renders a PDF page and reports the absolute interpreter to use. Read its result. On a later visit, `--check-only` detects missing or changed packages without downloading; run setup again to repair them. Preserve candidate records and existing environments. If packages are temporarily unavailable but the standard-library helpers can save correctly, the interview can continue with document export explicitly pending.

Dependency manifests ship with the skill because they are installation instructions, not installed third-party packages. Actual runtimes and downloads go in the nonsynced local cache, with only a small runtime pointer in the records. Tests and QA reports stay local and ignored. Preflight the chosen Python with `setup_runtime.py --preflight`; version detection alone is insufficient. If the harness blocks installation, explain the specific approval or missing capability; do not claim success. Fonts for a person's actual script, a DOCX renderer, web access and native scheduling are checked separately as described in the runtime reference.

The third-party installer may create a canonical `.agents` copy while targeting Claude. That is installer-managed skill content. If `/job-search` is not discovered yet, read the installed SKILL.md to continue; use one fresh session in the same project when the host needs it for native shortcut discovery. Do not loop on an unknown shortcut or initialize the candidate again.

## Updates

Before reporting a missing DOCX renderer, run the installed `setup_runtime.py --detect-renderers`; it checks standard LibreOffice locations as well as PATH. File creation and text extraction are separate from visual inspection. Apply the installed document quality gate before any upload, and pause that upload if the actual file cannot be viewed.

Use the same project and explicitly update only this skill. Preserve any locally changed installed version before replacement. The distribution directory must contain no private workspace. Check the new version's state schema support before use; v1 refuses unsupported schemas rather than migrating destructively. Reopen the existing private workspace and verify its workspace ID, revision and current next action. Do not initialize again. No update may overwrite profile, Q&A, applications or files.

## Optional daily routine

Onboarding offers a weekday morning search; installing the package never activates a schedule. Follow `references/routine.md`. Before scheduling, verify the selected IANA timezone with the private runtime. If its timezone database is unavailable, install `requirements-routine.txt` in that runtime only. Keep the generated prompt and schedule details in the private workspace. Use the actual desktop scheduler and verify its readback; CLI installation alone does not create a timer.
